3. `z = &x` stores the address of `x` into `z`.

Picture:

```
Memory:    [ ... | 5 | ... | 0x7ffe1234 | ... ]

                  x                z

```

## Why I'm pushing on this

Here's the thing you'll discover the hard way if I let it slide: when you write a class in C++, you split it into two files — a `.h` header (the interface, the "wall") and a `.cpp` (the implementation). ### Q3: "No idea" — perfect answer.

That's the right move. You didn't bullshit me. Here it is, plainly:

`#include <iostream>` is a **literal copy-paste**.

Before the compiler runs, a tool called the **preprocessor** reads through your file looking for any line that starts with `#`. When it sees `#include <iostream>`, it does this:

1. Finds the file `iostream` (it's just a text file living somewhere on your system, like `/usr/include/c++/11/iostream` or similar).
2. **Copies the entire contents of that file** and pastes it right where the `#include` line was.
3. Throws away the `#include` line.

Then — only then — does the actual compiler see your code. By the time the compiler looks at it, your `main.cpp` is no longer the small file you wrote. It's a much bigger file with thousands of lines of `iostream` content prepended to it.

That's it. That's the whole mechanism.

A demonstration. You write this:

cpp

```cpp
#include <iostream>

int main() {
    std::cout << "hi";
}
```

After the preprocessor runs, the compiler actually sees something like:

cpp

```cpp
// ...thousands of lines from iostream copied in here...
namespace std {
    class ostream { /* ... */ };
    extern ostream cout;
    // ...etc...
}
// ...end of iostream contents...

int main() {
    std::cout << "hi";
}
```

That's why you can use `std::cout` — because the _declaration_ of it got pasted into your file by the preprocessor.

You can actually see this happen. On your Zorin laptop, try:

bash

```bash
g++ -E main.cpp -o main_preprocessed.cpp
```

The `-E` flag tells g++ "stop after the preprocessor — don't actually compile." Open `main_preprocessed.cpp` and you'll see your tiny file is now ~30,000 lines. That's `iostream` and everything it transitively includes, copy-pasted in.

## The two errors you'll meet again and again

**Compiler error (Step 2): "undeclared identifier" / "Bag was not declared in this scope"** This is what you get when the compiler sees a name it has never heard of. In our scenario, the compiler reads `main.cpp`, has no `#include "Bag.h"`, hits the line `Bag b;`, and thinks: _"Bag? I don't know what a Bag is. I have no declaration for it. I can't even tell how big it is, what methods it has, anything. I refuse."_

This is what stops compilation in our missing-header scenario.

**Linker error (Step 4): "undefined reference to ..."** This is a _different_ problem. It happens when the compiler was happy (it saw the declaration in the header) but the linker can't find the actual _body_ of the function in any `.o` file.

Different example: imagine `main.cpp` correctly does `#include "Bag.h"`, so the compiler is happy and produces `main.o`. But you forgot to compile `Bag.cpp` (or it doesn't exist yet). Compilation succeeds. Then the linker runs, looks for `Bag::add`'s code, and finds nothing. _That_ gives you "undefined reference to `Bag::add`."

---

## The mental model in one line

- **Compiler error** = "I don't know what this _is_." (Missing declaration → fix the header.)
- **Linker error** = "I know what it is, but I can't find its _body_." (Missing definition → forgot to compile/link a `.cpp`, or forgot to write the implementation.)

This single distinction will save you hours of debugging. When you see the error message in your terminal, the _first_ thing you ask is: _which stage is yelling at me?_ That tells you where to look.

---

## Back to your hint-question — "How big is a Bag?"

You skipped this part of my question, so let me give you the answer because it makes the whole thing concrete.

When the compiler sees `Bag b;`, it needs to allocate memory for `b` on the stack. To do that, it needs to know **how many bytes a `Bag` takes up**. That information comes from the class declaration in `Bag.h` — once it sees that `Bag` has, say, an array of 100 ints and a count integer, it can compute: 100 × 4 + 4 = 404 bytes.

Without the header included, the compiler has no idea. It can't allocate. It must stop. **That's** the precise reason it can't proceed.

Compare this to what happens _with_ the header included but _without_ `Bag.cpp` being compiled:

- The compiler knows the size (404 bytes) — declaration is enough for that.
- The compiler knows `add` exists and takes an `int` — declaration is enough for that too.
- The compiler can produce `main.o` perfectly fine.
- Only when the linker tries to wire up the _actual instructions_ for `add` does the problem surface — because no `.o` file contains them.

That's why headers contain declarations and `.cpp` files contain definitions: the compiler only needs declarations to do its job; the linker is what needs definitions.

## Closing the loop — the diagnostic table you now own

You can now look at any C++ build error and ask:

|What you see|Stage|What's missing|How to fix|
|---|---|---|---|
|`error: 'X' was not declared in this scope`|Compiler|A declaration|Add the right `#include`, or write the declaration|
|`error: invalid use of incomplete type 'X'`|Compiler|The full class definition|Same — the header is missing or only forward-declares|
|`undefined reference to 'X'` (with `ld:`)|Linker|The function/method body|Compile and link the `.cpp` that defines it; or write the body if you forgot|
|`multiple definition of 'X'`|Linker|(the opposite problem)|Function body in a header without `inline`, or same `.cpp` linked twice|

Keep this table. You will reference it for years.

## A bonus observation: the warning you ignored

I notice in your terminal output earlier there was this:

```
Counter.cpp:17:1: warning: no return statement in function returning non-void [-Wreturn-type]
```

This is from before you fixed `value()`. The compiler caught that you declared `value()` to return an `int`, then wrote a body that didn't `return` anything. That's a _warning_, not an error — the program still compiled — but if you'd run it, calling `value()` would have returned **garbage** (whatever happened to be in the return register). That's an undefined-behavior bug that warnings catch for you.

**Habit to build now:** always compile with `-Wall -Wextra` to enable more warnings, and treat warnings as errors. Try this:

```bash
g++ -Wall -Wextra -Wpedantic main.cpp Counter.cpp -o counter_program
```
